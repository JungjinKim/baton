## 현재 상태
```!
echo "프로젝트: ${CLAUDE_PROJECT_DIR}"; grep -H '^단계:' "${CLAUDE_PROJECT_DIR}/.claude/work/"*.md 2>/dev/null || echo '(작업 문서 없음)'
```

## 진입 조건
- 호출 전문: `$ARGUMENTS`
- 작업 폴더는 `${CLAUDE_PROJECT_DIR}/.claude/work/`다.
- 대상 문서: 인자 slug(`$slug`)가 있으면 작업 폴더의 `$slug.md`, 없으면 위 목록의 미완 문서가 정확히 1개일 때 그 문서. 아니면 멈추고 묻는다.
- 대상 문서가 `단계: 구현`(수정 회차면 `리뷰`, 게이트2 지적·재검토로 다시 불렸으면 `승인대기`)이어야 한다. 아니면 멈추고 알린다.
- 스코프는 `## 구현`의 `### 변경 파일`이다(수정 회차면 그 회차 변경분, 절차 0의 전체 리뷰 조건에 들면 계획 Files와 누적 변경 파일 전체).
- 리뷰는 승인 범위 밖의 문제도 지적할 수 있다.
- 자동 수정은 고칠 수 있는 파일 안에서만 한다. 계획의 Files와 `## 구현`의 `### 계획 밖 변경`에 적힌 파일이다. 실행할 명령은 헤더 `검증 수단:`과 Task Verify, 부수효과 없는 읽기·검사로 제한한다.
- 고칠 수 있는 파일 밖 수정이나 승인되지 않은 명령이 필요하면 실행하지 않는다. 지적과 필요한 변경을 기록하고 `/baton:draft {slug} …`로 계획 개정을 안내한다. 사람 지적이면 절차 0대로 멈추고, 일반 리뷰면 절차 4대로 미해결 블로커로 올린다.
- 이 제한은 사람 지적 처리와 일반 리뷰의 자동 수정 모두에 적용한다.
- 사람에게 보이는 글(게이트 메시지·보고)은 작업 문서와 같은 언어(한국어·영어 등)로 쓴다. 호출 인자가 영문 slug뿐이어도 그렇다.

## 절차
0. 사람 지적·재검토 — 단계가 `승인대기`일 때 한다(게이트2 뒤에 사람이 다시 부른 것이다). 그 밖에는 1부터. 호출 전문에서 slug 바로 뒤 첫 낱말이 `재검토`면 재검토 호출이고, 아니면 사람 지적 호출이다. 다른 자리의 `재검토`는 지적의 일부로 본다.
   - 전체 리뷰 조건: 재검토 호출이거나, `## 인계`의 리뷰 기준이 없거나 현재 파일과 다르면 1에서 계획 Files와 누적 변경 파일 전체로 리뷰한다. 변경이 없고 기준만 없던 경우도 같다. 이전 사람 테스트 결과는 아래에서 블로커를 정할 때만 쓰고 새 게이트2 표에는 옮기지 않는다.
   - 재검토 호출: 지적과 `FAIL`을 찾지 않고 무엇이 달랐는지 묻지도 않는다. 계획의 Files와 누적 변경 파일을 다시 확인하고 Verify → 빌드를 거쳐 1로 간다. 확인 중 AC·Spec 변경이나 고칠 수 있는 파일 밖 수정이 필요하면 아래 개정 조건을 따른다.
   - 사람 지적 호출: 블로커는 호출 전문에서 slug 뒤에 적힌 지적, 그리고 `## 인계`의 사람 테스트 중 `FAIL`로 기록된 항목과 거기 적힌 메시지다. 둘 다 없으면 무엇이 기대와 달랐는지 묻고 멈춘다. 전체 리뷰 조건에 들어도 블로커를 먼저 고치고 그 뒤 1로 간다.
   - 블로커마다 원인을 코드에서 찾아 고친다 → Verify → 빌드 → `## 구현`에 수정 회차·사람 지적·파일 기록 → 1로 간다. 고친 것도 fresh 리뷰를 거친다.
   - 지적이 계획 밖 변경을 되돌리는 것이면 되돌린다(사본이 있으면 사본으로). 되돌린 파일은 `### 계획 밖 변경`과 `### 변경 파일`에서 뺀다. 그 변경이 채우던 AC를 고칠 수 있는 파일 안에서 다시 채울 수 있으면 채우고 1로 간다. 채울 수 없으면 되돌린 상태를 두고 아래 개정 조건을 따른다.
   - 개정 조건: AC·Spec을 바꿔야 풀리거나 고칠 수 있는 파일 밖을 고쳐야 풀리면 고치지 않는다. 단계를 `계획`으로 되돌리고 `/baton:draft {slug} …`를 안내하고 끝낸다.
1. 입력 준비 — 작업 폴더의 `scratch/`에 파일 셋(`{slug}.diff`, `{slug}.ac.md`, `{slug}.review-state.md`)을 만든다. 단계를 `리뷰`로 바꾼다.
   - 리뷰 기준: diff를 만들기 전에 대상 루트의 절대 경로와 계획 Files·누적 변경 파일의 합집합을 `{slug}.review-state.md`에 기록한다. 디렉터리·glob은 파일 목록으로 펼치고, 경로별 파일 바이트의 SHA-256을 적는다. 삭제된 경로는 `없음`으로 적고 목록에서 빼지 않는다. 작업 문서·scratch 같은 baton 자체 기록은 대상에서 뺀다. 기준은 1을 지날 때마다 다시 적는다. 한 회차 안에서는 덮어쓰지 않는다.
   - diff: 파일마다 만들어 잇는다 — 구현 전 사본(`snapshots/{slug}/`)에 있는 파일은 사본 대비 `diff -u`, 없는 파일은 `git diff HEAD -- <file>`. 추적되지 않는 새 파일은 전문을 덧붙인다.
   - AC: `## Spec`의 AC만 추출한다(개정이 있으면 최신 개정 반영).
   - 넘기기 전에 diff·AC·리뷰 기준 파일이 있고 비어 있지 않은지 확인한다. diff가 비면 멈추고 알린다. 해시를 읽지 못한 파일이 있으면 그 경로와 사유를 보이고 멈춘다.
2. `Agent(baton:reviewer)`를 부른다. 프롬프트는 두 줄: "diff: <경로>" / "AC: <경로>". 계획·구현 서사·"확인했음" 목록은 넘기지 않는다.
3. 결과를 `## 리뷰 n회차`에 기록한다: 블로커 / 중요 / 잔여 리스크·테스트 공백. 블로커는 Critical 전부와 AC를 깨는 Important다.
4. 블로커가 1건 이상이면 블로커만 고친다(중요 중 정책성은 "변경 없음", 나머지는 함께) → Verify → 빌드 → `## 구현`에 수정 회차와 파일 기록 → 1로 돌아간다. 3회를 넘기면 멈추고 이력을 붙여 사람에게 올린다.
   - AC·Spec을 바꿔야 풀리거나, 고칠 수 있는 파일 밖 수정이나 승인되지 않은 명령이 있어야 풀리는 블로커는 여기서 고치지 않는다. `미해결 블로커`로 기록하고 게이트2 첫머리에 올린다 — 수용할지 개정할지는 사람이 정한다. 같은 회차의 다른 블로커는 그대로 고친다.
5. 고칠 수 있는 블로커가 0이면 커밋 위생을 본다: `git status --short` 인벤토리 / 시크릿·자격증명 / 제외 대상(로그·빌드 산출물·로컬 설정·`.claude`) / 무관 변경을 분리할 수 있는지.
6. 게이트2 — 한 통으로 제시하고 같은 내용을 작업 문서의 `## 인계` 절(절 이름 그대로)에 기록한다. 작업 문서와 같은 언어로 쓴다. 단계 `승인대기`, 턴을 끝낸다.
   - `## 인계`는 게이트2마다 새로 쓴다. implement가 적은 무관 변경 기록은 그대로 둔다. 앞선 게이트2가 있었으면(사람 지적·재검토·개정 뒤) 앞선 사람 테스트 결과와 미해결 블로커는 표에 남기지 않고 한 줄로 줄인다(`이전 결과: 2번 FAIL → 수정 1회차에서 고침`). FAIL이던 항목은 새 표에 다시 넣는다. 미해결 블로커는 이번 리뷰에서 나온 것만 싣는다.
   - 첫 줄은 한 문장 요지. 미해결 블로커가 있으면 그 바로 아래에 실패 시나리오와 함께 적는다.
   - 계획 밖 변경: `## 구현`에 `### 계획 밖 변경`이 있으면 미해결 블로커 다음에 그대로 옮긴다. 되돌리려면 `/baton:inspect {slug} <되돌릴 것>`이라고 적는다.
   - AC 판정: PASS는 증거가 있을 때만 — 명령 Verify는 실행 결과, `확인:` Verify는 충족 위치(`파일:라인`). 없으면 `미검증`.
   - 잔여 리스크: 리뷰가 남긴 것과 검증하지 못한 것. `## 구현`의 빌드 기록에 `새 경고: 미확인(사유)`가 있으면 사유와 함께 싣는다.
   - 리뷰 기준: `scratch/{slug}.review-state.md` 경로. signoff는 이 기준과 현재 파일이 같은지 확인한다.
   - 사람 테스트 목록: Spec의 `### 사람 테스트`를 먼저 옮기고, 구현과 리뷰로 새로 드러난 것을 더한다 — 바꾸지 않았는데 영향받는 곳(코드면 호출 지점, 글이면 그 글에 기대는 문서·절차) / 상태 전이·동시성 / 화면에 안 보이는 것(로그·DB·외부 연동 메시지·와이어 형식). 명령 Verify가 이미 증명한 것(문구 일치·개수·존재)은 싣지 않는다. 표(`# | 해 볼 것 | 기대`)로 전부 싣는다 — 문서를 보라고 넘기지 않는다.
   - 커밋 초안: 저장소의 기존 커밋 관행(`git log --oneline -15`)을 따른 메시지 + 경로 지정 add 명령.
   - OQ · 정책성 보류 · 범위 밖 발견. 블로커는 범위 밖 발견으로 내려 적지 않는다 — 미해결 블로커에 둔다.
   - 끝에 "테스트 후 `/baton:signoff {slug}`, 결과물 지적은 `/baton:inspect {slug} <기대와 달랐던 것>`, AC 변경은 `/baton:draft {slug} …`". 미해결 블로커가 있으면 "수용이면 `/baton:signoff`, 아니면 `/baton:draft {slug} …`"를 덧붙인다.

## 사람 테스트 항목 쓰는 법
- 한 항목에 한 가지만, y/n으로 답할 수 있는 문장으로 쓴다. 관찰값이나 메시지가 필요하면 "없으면 none"을 붙인다.
- 사람이 해 보고 관찰할 수 있는 것만 넣는다. 정책·제품 결정을 묻는 것은 테스트가 아니라 OQ다.
- 결과는 `/baton:signoff`가 세션 안에서 항목별로 묻는다. 별도 스크립트나 터미널을 요구하지 않는다.

## 완료 조건 → 다음
- 고칠 수 있는 블로커 0(미해결 블로커는 게이트2 첫머리에 명시) / 잔여 리스크 명시(근거 없는 "문제없음" 금지) / 커밋 위생 / 수정 회차가 있었으면 그 회차의 빌드 / 리뷰 기준 기록 / 단계 `승인대기`.
- 승인은 사람이 테스트 후 `/baton:signoff {slug}`를 부르는 것이다. 커밋하지 않는다.
- 지적이 Spec·AC 변경이면 여기서 AC도 코드도 고치지 않는다. 단계를 `계획`으로 되돌리고 `/baton:draft {slug} …`(같은 문서 개정)을 안내한다.

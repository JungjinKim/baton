## 요청
$ARGUMENTS

## 진입 조건
- 요청이 비어 있으면 무엇을 할지 묻고 멈춘다.
- 작업 폴더는 `${CLAUDE_PROJECT_DIR}/.claude/work/`다. 없으면 만든다. 고칠 소스가 이 프로젝트 밖에 있어도 작업 문서는 여기에 둔다.
- 대상은 코드가 아니어도 된다(문서·설정·데이터·프롬프트). 그때 아래의 '코드'는 고칠 대상 파일로, '동작'은 그 파일을 읽거나 쓰는 쪽이 얻는 결과로 읽는다.
- 만들 문서 `{slug}.md`가 위 목록에 미완(`단계: 완료` 아님)으로 있으면 덮어쓰기 전에 묻는다.
- 요청이 위 목록의 미완 문서 slug로 시작하면 개정이다(승인 뒤 Spec 변경). 덮어쓰지 않고 `## Spec`에 `### n차 개정`(바뀐 AC·전제), `## 계획`에 추가 Task를 적은 뒤 절차 6(정규만)·7·8을 다시 거친다. 기존 `## 구현`·`## 리뷰`는 남긴다.
- 요청의 첫 낱말이 위 묶음 목록의 `[ ]` 작업 slug이고 그 작업 문서가 아직 없으면 묶음의 다음 작업이다 → `BUNDLE.md`의 "다음 작업".
- 요청의 첫 낱말이 묶음 이름(`{묶음}.bundle.md`의 `{묶음}`)이면 묶음 개정이다 → `BUNDLE.md`의 "묶음 개정".
- slug와 묶음 이름은 첫 낱말 전체로 맞춘다 — `a-b`는 `a-b-c`와 다르다.

## 문서
- slug는 영문 소문자 kebab `{영역}-{요지}`. 영역은 모듈·패키지·서비스 이름이다(코드가 아니면 문서 묶음·주제 이름).
- 유형은 대상의 종류가 아니라 변경의 성격이다: 새 내용 → 기능, 틀린 것 고침 → 수정, 뜻을 바꾸지 않는 재구성 → 리팩터. 문서화는 코드 토큰을 바꾸지 않고 주석·설명만 덧붙이는 작업이다 — 문서 파일 자체가 결과물이면 앞의 셋에서 고른다.
- 골격은 이 문서 끝의 "작업 문서 골격"을 그대로 쓴다. 경량은 전체 30줄 안팎, 정규는 60줄 안팎.
- 이 스킬은 `## 구현 메모`까지만 쓴다. `## 구현`·`## 리뷰 n회차`·`## 인계`는 뒤 단계가 덧붙인다. 다른 baton 스킬의 파일은 읽지 않는다.

## 절차
1. 파악 — 요청이 가리키는 파일과 기존 동작을 코드로 직접 확인해 `## 배경`에 `파일:라인`으로 적는다. 위임은 읽을 파일 수가 두 자릿수일 때만.
   - 프로젝트 문서: `docs/agent/`가 있으면 `gotchas.md`를 먼저 읽고, 고칠 위치를 찾을 때 `overview.md`를 쓴다. 문서와 코드가 다르면 코드를 따르고 보고에 적는다. 없으면 게이트1 끝에 "`/baton:survey`으로 프로젝트 문서를 만들 수 있다"를 한 줄 덧붙인다(멈추지 않는다).
   - 미확인 질문: 읽은 프로젝트 문서의 `## 확인 못 함`에 고칠 대상에 걸린 질문이 있으면 절차 2에서 같이 묻는다. 받은 답은 `### 전제`에 적고 줄 끝에 `(확인 못 함의 답 {YYYY-MM-DD})`를 붙인다 — 종결 때 프로젝트 문서로 옮길 재료다.
   - 검증 수단: `docs/agent/commands.md`가 있으면 거기서 먼저 고른다(`실행 확인` 표시 우선). 없거나 맞는 명령이 없으면 저장소 파일에서 찾는다 — 매니페스트(`package.json` scripts · `*.sln`/`*.csproj` · `pyproject.toml` · `pom.xml`/`build.gradle` · `Cargo.toml` · `go.mod` · `Makefile`), CI 설정, README. 대상 파일을 덮는 가장 좁은 범위를 골라 명령과 출처를 헤더 `검증 수단:`에 적는다. 전체 빌드가 분 단위로 길거나 돌릴 환경이 없거나 대상이 빌드되는 것이 아니면(문서·설정·데이터·프롬프트) `빌드 생략(사유)`와 대체 수단을 적는다 — 대상을 검사하는 저장소의 명령(문법 검사·린트·단위 테스트·스키마 검증·링크 검사)이 있으면 그것, 없으면 `대체 없음`으로 적고 검증은 Task Verify가 진다. 추측한 명령은 적지 않는다 — 있어야 할 명령을 못 찾으면 절차 2에서 묻는다.
   - 준비: 검증 수단을 돌리기 전에 필요한 환경 준비(의존성 설치·코드 생성)가 있으면 헤더 `준비:`에 명령과 부수효과(네트워크·디스크)를 적는다. 설치는 lockfile을 바꾸지 않는 형태만 쓴다(`npm ci` · `pnpm install --frozen-lockfile` · `yarn install --immutable` · `pip install -r requirements.txt` · `uv sync --frozen`). lockfile이 없으면 `준비:`에 쓰지 않고 절차 2에서 묻는다. 필요 없으면 `준비: 없음`.
   - 동기화: 대상이 git 저장소고 upstream이 있으면 `git fetch` 뒤 `git status -sb`·`git diff --stat HEAD..@{u}`로 뒤처진 커밋 수와 대상 파일 겹침을 헤더 `동기화:`에 적는다. 겹치면 게이트1 전에 멈춰 pull 여부를 묻는다. pull은 하지 않는다. git이 아니거나 upstream이 없으면 `해당 없음`.
2. 질문 — 어떻게 읽느냐에 따라 결과물이 달라지는 것만 묻는다. 코드로 확정되는 것은 스스로 확인해 전제로 적는다. 입력 자료(요구 문서·이전 작업 문서)와 코드가 다르면 묻는다. 다음 둘은 전제로 채우지 않고 반드시 묻는다: 기존 사용자 가시 동작(확인창·검증·안내)을 빼거나 바꾸는 가정 / 외부에서 들어온 값을 내부 식별자·키로 쓸 때 값의 범위와 존재 검증. 선택지 2~4개를 붙여 한 턴에 `AskUserQuestion`으로 묶어 묻는다. 물을 수 없는 환경(비대화 실행)이면 가장 보수적인 선택을 전제로 적고 OQ에 "확인 필요"로 남긴다.
   - 분할 제안: `## 묶음`의 조건에 들면 분할안을 이 질문과 한 턴에 묻는다. Spec은 그 답을 받은 뒤에 쓴다.
3. Spec — AC("[주어]가 [조건]일 때 [동작]해야 한다", 번호) / 사람 테스트(Verify로 못 재는 것만) / 전제(코드로 도출 못 하는 결정만, 기각한 대안은 이유와 함께) / 범위 밖 / OQ. 문서화 유형은 대상 파일의 기존 주석 관행(항목당 줄 수·최대 글자 수)을 재서 수치 AC로 넣는다. 글이 결과물인 작업도 같은 자리의 기존 글 관행(절 구성·용어·표기)을 AC로 넣는다. 기존 글의 최댓값을 상한 수치로 옮기지 않는다.
4. 규모 — 다섯 조건이 전부 참이면 경량, 하나라도 거짓이면 정규. 헤더에 근거 한 줄.
   - 지목된 파일 3개 이하, 변경 50줄 안팎
   - 공개 계약 불변(데이터 스키마·외부 API·와이어 형식·공용 모듈·의존성 — 코드가 아니면 다른 파일·도구·사람이 기대는 이름·경로·형식·절차)
   - 상태 전이·동시성 없음
   - 탐색 불필요(고칠 위치가 이미 특정됨)
   - 보안 표면 없음(인증·인가·입력 검증·민감정보)
5. 계획 — Task마다 `AC · Files · Verify(명령 → 기대 결과)`. Verify는 헤더 `검증 수단:`에서 고르거나 그 Task만 재는 명령(grep·단위 테스트·스크립트)을 쓴다. 명령으로 잴 수 없는 AC(글의 내용·구성)는 `확인: {읽을 곳} → {통과 기준}`으로 쓴다 — 기준은 누가 읽어도 같은 판정이 나오는 관찰(있다/없다 · 개수 · 순서 · 일치)로 쓰고, AC가 수치·필수 항목을 요구하면 그 부분만 명령으로 잰다. 같은 사실을 여러 명령으로 겹쳐 재지 않는다. Verify가 통과하는지 보려고 결과물을 미리 만들어 보지 않는다 — 계획은 읽기만 한다. 판단이 갈리는 것(어조·설득력)은 Verify가 아니라 Spec의 `### 사람 테스트`에 넣는다. 문서화 유형(코드 토큰 불변)은 넣을 본문 초안까지 쓴다 — 초안은 3의 수치 AC 안에 들어야 하고 Verify가 그 수치를 잰다.
   - 나누기: Task 하나는 AC 하나 이상을 끝까지 충족시키는 단위다 — 그 AC에 필요한 층(저장·로직·호출부·화면·테스트)을 한 Task의 Files에 모으고, Verify는 그 AC를 잰다. 층별로 나누면(컬럼 → API → 화면) 마지막 Task 전에는 어떤 AC도 잴 수 없다. AC 하나가 Task 하나에 담기에 크면 AC를 더 좁은 동작으로 나눈다(절차 3으로).
   - 준비 Task: 뒤 Task에 꼭 필요한 재구성(동작 불변)은 동작을 바꾸는 Task와 섞지 않고 맨 앞 Task로 뗀다. `AC: 없음(준비 — Task n에 필요한 이유)`로 적고, Verify는 기존 동작이 그대로인지를 잰다.
   - 순서: 앞 Task까지만 끝난 상태에서도 대상이 깨지지 않게(헤더 `검증 수단:` 통과) 잡는다 — implement가 중간에 끊겨도 깨진 채 남지 않는다. 한쪽만 바꾸면 깨지는 짝(정의↔호출부 · 스키마↔소비자)은 한 Task에 모은다. 쓰는 곳이 많아 한 Task에 못 모으는 이름·형식 변경은 세 Task로 나눈다: 새 형태를 옛 형태 옆에 추가 → 쓰는 곳을 옮김 → 옛 형태 삭제. 이 작업에서 옮길 수 없는 쓰는 곳(다른 저장소)이 남으면 옛 형태를 남기고 삭제는 `### 범위 밖`에 적는다.
6. 검증 — 정규만. 작업 문서의 `## Spec`·`## 계획`만 작업 폴더의 `scratch/{slug}.plan.md`로 추출한다(배경 서사·결론 제외). `Agent(baton:doubter)`를 부르고 프롬프트는 한 줄 "입력: <스크래치 경로>". 내용은 프롬프트에 붙여 넣지 않는다. 발견은 보강·과잉 양방향으로 반영하고 `## 검증`에 요약한다. 최대 2사이클, 남은 것은 OQ로.
7. 인계 점검 — 구현은 이 대화를 못 본 새 세션이 작업 문서만 읽고 한다. 게이트1 전에 "문서만으로 구현할 수 있나?"를 확인한다.
   - 대화에서 정했는데 문서에 없는 것(사람의 답, 고친 AC·전제)은 Spec에 넣는다.
   - 탐색 중 알게 된 것 중 구현자가 다시 찾느라 헤맬 것(함정, 먼저 읽을 파일, 해 봤다가 버린 접근과 이유)은 `## 구현 메모`에 최대 5줄로 적는다. `docs/agent/`에 이미 있는 것은 링크만. 적을 것이 없으면 절째 뺀다.
   - 구현 메모는 읽을 정보다. 실행할 명령은 쓰지 않는다 — 명령은 헤더 `준비:`·`검증 수단:`과 Task Verify에만 둔다(implement는 거기 있는 명령만 돌린다). 할 것으로 쓰고 금지는 짝으로만 붙인다 — 예: "빌드 확인은 lint·단위 테스트로 (`npm run build`는 DB 마이그레이션 동반)".
8. 게이트1 — 한 통으로 제시한다: 규모 · AC · 사람 테스트 · 전제 · 파일(변경 요지) · Verify · OQ. 사람이 읽고 승인하는 글이다.
   - 첫 줄은 한 문장 요지(무엇을·왜).
   - 제목과 용어는 풀어 쓴다 — AC는 "완성 기준", 사람 테스트는 "직접 해 보실 것", 전제는 "요청에 없어서 제가 정한 것", Verify는 "확인 방법", OQ는 "아직 못 정한 것". 작업 문서 안의 절 이름은 그대로 둔다.
   - AC와 사람 테스트는 표(`# | 상황 | 기대`). 셀은 짧게, 긴 근거는 표 밖 문장으로.
   - 전제는 요청과 다른 점, 그리고 요청이 말하지 않아 정한 것을 문장으로.
   - 준비 Task가 있으면 무엇을 왜 재구성하는지 한 줄로 보인다 — 요청에 없던 변경이다.
   - 기계 Verify는 한 줄 요약. 단 `검증 수단:`에 없는 Verify 명령은 명령 그대로 보인다(grep·diff 같은 부수효과 없는 읽기·검사는 요약으로 둔다). `검증 수단:`과 `준비:`는 명령 그대로 보인다 — implement는 이 둘과 Verify만 실행하므로 사람이 여기서 확인해야 한다. `준비:`가 `없음`이면 보이지 않는다.
   - 문서화 유형은 초안 전문을 그대로 보인다(요지로 줄이지 않는다).
   - 끝에 "승인이면 `/clear` 후(또는 새 세션에서) `/baton:implement {slug}`, 고칠 것은 여기서 말해 달라". 새 세션을 권하는 이유(계획 대화의 가정이 구현에 섞이지 않고, 문서의 구멍이 드러난다)를 한 줄 붙인다.
   - 단계 `계획`으로 두고 턴을 끝낸다.

## 묶음
큰 요청을 작업 문서 여러 개로 나누고, 뒤 작업의 문서는 앞 작업이 끝난 뒤의 코드로 쓴다.
- 분할 제안 — 절차 1이 끝난 시점에 본다. 아래 둘이 다 참이면 분할을 제안한다. 강제가 아니다.
  - 요청이 따로 확인하고 따로 내놓을 수 있는(커밋·배포·전달) 결과 둘 이상으로 나뉜다 — 결과 하나만 끝나도 사람이 해 보거나 읽어 보고 확인할 수 있고 대상이 깨지지 않는다. 그것만으로는 확인할 것이 없는 조각(코드면 스키마만·API만, 글이면 목차만·용어 정리만)은 결과가 아니다.
  - 그리고 다음 중 하나: 앞 결과를 만들어 봐야 답이 나오는 질문이 뒤 결과의 Files·Verify를 가른다 / 예상 변경 파일이 두 자릿수다. 뒤 결과가 앞 결과가 만든 것을 쓴다는 것만으로는 앞쪽에 해당하지 않는다 — 문서에 적힌 대로 만들어지는 것은 지금 계획할 수 있다.
- `BUNDLE.md` — 다음 중 하나면 `${CLAUDE_SKILL_DIR}/BUNDLE.md`를 먼저 읽고 따른다. 분할안·묶음 문서의 형식과 묶음에 속한 작업 문서의 헤더·게이트1·완료 조건이 거기 있다. 어느 것도 아니면 읽지 않는다.
  - 위 분할 조건에 들었다
  - 진입 조건에서 묶음의 다음 작업이거나 묶음 개정으로 판정됐다
  - 개정할 작업 문서의 헤더에 `묶음:` 줄이 있다

## 완료 조건 → 다음
- AC 전부 테스트 가능한 형식 / Task 3필드 전부 / 준비 Task를 뺀 Task마다 끝까지 충족시키는 AC 하나 이상 / `검증 수단:` 출처(생략이면 사유) 명기 / 검증 블로커 0(경량은 "검증 생략" 명기) / 대화에서 정한 것 전부 문서에 있음 / 단계 `계획`.
- 승인은 사람이 `/baton:implement {slug}`를 부르는 것이다. 이 스킬 안에서는 게이트가 닫히지 않는다 — 지적이 오면 대화로만 답하지 말고 문서를 고쳐(절차 7 포함) 게이트1을 다시 제시하고, "좋아요"·"알아서 해" 같은 답에는 같은 안내를 반복한다. 구현을 시작하지 않는다.

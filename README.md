# baton

Claude Code에게 일을 맡길 때, 중간중간 사람이 확인하면서 진행할 수 있게 도와주는 플러그인이에요.

AI는 코드를 읽을 수 있어도, 이 작업이 왜 필요한지와 무엇을 바꾸면 안 되는지는 몰라요. 그건 사람이 알려 줘야 해요. baton은 사람이 알려 준 것을 작업 문서로 남기고, 사람이 그 문서를 승인한 뒤에 AI가 그 문서대로 구현하게 해요. 레거시 코드를 고치면서 직접 쓰던 작업 절차를 플러그인으로 옮긴 거예요.

일을 **계획 → 구현 → 리뷰 → 마무리** 네 단계로 나누고, 그 사이에 사람이 한 번씩 멈춰서 확인하는 자리(**게이트**)를 두 곳 둬요. 이어달리기에서 바통을 넘기듯, 게이트마다 사람이 바통을 받아 "좋아, 다음 단계로" 하고 넘겨 주는 방식이에요.

이런 점을 노리고 만들었어요.

- 사람이 계획을 승인하기 전에는 구현을 시작하지 않아요. 구현 중에도 승인할 때 보여 준 명령과 읽기 전용 확인만 실행하도록 되어 있어요.
- 무엇을 확인했고 무엇을 아직 확인하지 못했는지가 작업 문서에 남아요.
- 특정 언어나 저장소에 묶이지 않아요. 코드가 아닌 문서·설정·데이터 작업에도 쓸 수 있어요.

> 이 규칙들은 AI에게 주는 지시문(`SKILL.md`)이에요. "사람만 부를 수 있다"는 규칙은 Claude Code가 실제로 막아 주지만, 나머지는 권한 설정처럼 기술적으로 막는 장치가 아니에요. 게이트에서 보여 주는 내용은 꼭 읽어 주세요.

## AI가 코드에서 알 수 없는 것

파일 위치, 지금 동작, 빌드 명령은 AI가 코드를 읽어서 알아내요. 아래 것들은 코드에 없어서 사람이 알려 줘야 해요. baton은 사람에게 받은 답을 파일에 적고, 사람이 그 파일을 확인하게 해요.

| AI가 알 수 없는 것 | 적어 두는 곳 | 사람이 확인하는 때 |
|---|---|---|
| 이상해 보이는 레거시 동작이 의도인지 버그인지 | survey가 `docs/agent/gotchas.md`의 `## 확인 못 함`에 질문으로 남겨요. draft는 고칠 곳에 걸린 질문을 사람에게 묻고, 답을 작업 문서의 `### 전제`에 적어요 | 첫 번째 게이트 |
| 코드에 없는 정책 (예: 대출 준비를 취소해도 예약 순번은 그대로 둔다) | 작업 문서의 `### 전제` | 첫 번째 게이트 |
| 명령이 어느 DB에 붙는지, 돌려도 되는지 (예: 빌드 스크립트가 DB 마이그레이션까지 실행) | `gotchas.md`의 `## 환경`, 작업 문서 맨 위의 `검증 수단:`·`준비:` | 첫 번째 게이트에서 실행할 명령을 보여 줘요 |
| 전에 해 봤다가 버린 방법과 그 이유 | 작업 문서의 `### 전제`(고르지 않은 방법과 이유)와 `## 구현 메모`(구현자가 다시 해 보지 않게). 오래 지킬 선택은 `gotchas.md`의 `## 결정` | 첫 번째 게이트(`### 전제`만 보여 줘요. `## 구현 메모`는 작업 문서를 열어서 봐요) |
| 지난 대화에서 정한 것 | 대화에서 정한 것은 첫 번째 게이트 전에 작업 문서로 옮겨요. 구현은 새 대화에서 작업 문서만 보고 해요 | 첫 번째 게이트 |
| 어떤 상태가 "끝난 것"인지 | 작업 문서의 완료 기준(AC)과 사람이 테스트할 항목 | 첫 번째 게이트에서 승인하고, 마무리(signoff) 때 테스트 결과를 적어요 |

AI가 묻지 않고 스스로 정한 것도 `### 전제`에 적혀요. 첫 번째 게이트는 AI가 요청을 어떻게 이해했는지 확인하는 자리예요. `### 전제`를 "요청에 없어서 제가 정한 것"이라는 제목으로 따로 보여 주니, 거기부터 읽어 주세요. 작업 문서가 실제로 어떻게 채워지는지는 [`examples/`](examples/)의 예시에서 볼 수 있어요.

처음이라면 [`docs/guide.md`](docs/guide.md)를 한번 읽어 보세요. 예시 하나로 네 단계를 차근차근 따라가 볼 수 있어요.

## 설치

Claude Code에서 아래 두 줄을 입력하면 돼요.

```
/plugin marketplace add JungjinKim/baton
/plugin install baton@jungjinkim
```

저장소를 내려받아 두었다면 첫 줄의 `JungjinKim/baton` 자리에 그 폴더 경로(예: `~/baton`, `D:\tools\baton`)를 넣어도 돼요.

설치 없이 잠깐 써 보고 싶다면 이렇게 실행해도 돼요.

```
claude --plugin-dir <baton 폴더 경로>
```

## 이렇게 써요

예를 들어 "도서 대출 준비를 취소할 수 있게 해 줘"라는 일을 맡긴다고 해 볼게요.

**1. 계획 세우기**

```
/baton:draft 도서 대출 준비를 취소할 수 있게 해 줘
```

AI가 코드를 읽어 보고, 답에 따라 결과가 달라지는 것만 물어본 뒤 작업 문서를 써요. 그리고 "이렇게 만들려고 해요" 하고 완료 기준·바꿀 파일·실행할 명령을 보여 준 다음 멈춰요. 여기가 **첫 번째 게이트**예요.

**2. 구현하기**

계획이 마음에 들면 `/clear`로 대화를 비우고(권장) 이렇게 불러 주세요.

```
/baton:implement <slug>
```

계획대로 구현하고, 계획에 적힌 방법으로 검증하고, 빌드할 게 있으면 빌드까지 해요. 끝나면 리뷰 단계(inspect)로 알아서 넘어가요. 리뷰는 구현 대화를 보지 않은 별도 에이전트가 맡고, 막히는 문제가 나오면 고친 뒤 다시 리뷰해요(최대 3회).

리뷰가 끝나면 "이건 직접 확인해 주세요" 하고 사람이 테스트할 항목과 커밋 메시지 초안을 보여 주고 멈춰요. 여기가 **두 번째 게이트**예요.

**3. 마무리하기**

직접 테스트해 보고 나서 불러 주세요.

```
/baton:signoff <slug>
```

테스트 항목마다 결과를 물어서 기록하고, 커밋 초안을 최종 상태에 맞춘 뒤 작업 문서를 `done/`으로 옮겨요. 테스트에서 기대와 다른 항목이 있으면 마무리하지 않고 어디로 되돌아갈지 알려 줘요.

커밋은 직접 하시면 돼요. 맡기고 싶으면 `/baton:signoff <slug> 커밋까지`라고 불러 주세요. push는 하지 않아요.

> `<slug>`는 작업 이름이에요(예: `loan-cancel-ready`). draft가 정해서 알려 줘요. implement·inspect·signoff는 진행 중인 작업이 하나뿐이면 slug를 생략해도 돼요. 개정(`/baton:draft <slug> <바뀐 내용>`)은 slug로 시작해야 해요.
>
> 새 프로젝트에서 처음 쓴다면 시작 전에 `/baton:survey`를 한 번 돌려 두는 걸 권해요. 프로젝트 구조·명령·주의할 점을 문서로 정리해 두면, 이후 단계들이 그 문서를 참고해요. 없어도 다른 단계는 잘 돌아가요.

## 명령 한눈에 보기

| 명령 | 언제 부르나요 | 무엇이 나오나요 |
|---|---|---|
| `/baton:survey` | 프로젝트에서 처음 한 번, 코드가 많이 바뀌었을 때 | 프로젝트 안내 문서(`docs/agent/`, `AGENTS.md`, `CLAUDE.md`) |
| `/baton:draft <요청>` | 일을 시작할 때 | 작업 문서, 첫 번째 게이트 |
| `/baton:implement <slug>` | 계획이 마음에 들 때 | 구현, 이어서 자동 리뷰, 두 번째 게이트 |
| `/baton:inspect <slug> <달랐던 점>` | 테스트해 보니 기대와 다를 때 | 수정 후 다시 리뷰 |
| `/baton:signoff <slug>` | 테스트를 마쳤을 때 | 결과 기록, 마무리 |
| `/baton:handoff [다음에 할 일]` | 대화가 길어져서 새 세션으로 넘어가고 싶을 때 | 인계 문서(`.claude/work/handoff/`) |

## 이럴 땐 이렇게

| 이런 상황이라면 | 이렇게 해 보세요 |
|---|---|
| 첫 번째 게이트에서 계획이 마음에 안 들어요 | 그 자리에서 말로 알려 주세요. 문서를 고쳐서 다시 보여 줘요 |
| 승인한 뒤에 요구 사항이 바뀌었어요 | `/baton:draft <slug> <바뀐 내용>` |
| 구현하다가 멈췄어요 | 멈춘 이유를 확인하고 `/baton:draft <slug> …`로 보완한 뒤 implement를 다시 불러 주세요. 설치를 기다리는 멈춤은 아래 줄을 보세요 |
| 외부 패키지 설치를 기다리며 멈췄어요 | 보여 준 설치 명령을 직접 돌린 뒤 `/baton:implement <slug>`를 다시 불러 주세요. draft는 거치지 않아요 |
| 테스트해 보니 기대와 달라요 | `/baton:inspect <slug> <달랐던 점>` |
| 리뷰에서 못 고친 문제가 남았지만 알고 마무리하고 싶어요 | `/baton:signoff <slug> 수용` |
| 요청이 너무 커요 | 일정 조건에 들면 draft가 여러 작업으로 나누자고 제안해요 ([guide 4.3절](docs/guide.md)) |
| 내일 다른 세션에서 이어 하고 싶어요 | `/baton:handoff`로 인계 문서를 만들고, 새 세션에서 "인계 문서 읽고 이어서 진행해"라고 말해 주세요 |

## 알아 두면 좋은 것

**"좋아요"라고 말하는 것만으로는 다음 단계로 넘어가지 않아요.**
승인은 명령으로 해요. 첫 번째 게이트는 `/baton:implement`, 두 번째 게이트는 `/baton:signoff`를 불러야 넘어가요.

**게이트에서 보여 준 명령만 실행해요.**
계획에 없던 설치·배포·DB 변경·외부 호출이 필요해지면, 실행하지 않고 멈춰서 물어봐요. 파일을 읽거나 `git status`처럼 아무것도 바꾸지 않는 확인은 따로 묻지 않아요.

**구현은 새 세션에서 하는 게 좋아요.**
implement는 이전 대화가 아니라 작업 문서, `docs/agent/` 문서, 코드만 보고 일해요. 그래서 `/clear` 후에 부르길 권해요. 계획할 때의 가정이 구현에 섞이지 않고, 문서에 빠진 게 있으면 드러나거든요.

**AI가 스스로 부를 수 있는 건 두 가지뿐이에요.**
구현이 끝난 뒤의 리뷰(inspect)와, 세션을 넘길 때의 인계(handoff)예요. 나머지는 사람만 부를 수 있어요.

## 어떤 파일이 생기나요

모두 프로젝트 폴더(Claude를 시작한 폴더) 안에 생겨요. 따로 설정 파일을 만들 필요는 없어요.

```
.claude/work/              baton의 작업 공간
  {slug}.md                작업 문서 (작업 하나에 파일 하나)
  {묶음}.bundle.md         큰 요청을 나눴을 때의 작업 목록
  ledger.md                작업마다 한 줄씩 남는 기록
  done/                    끝난 작업 문서
  handoff/                 세션 인계 문서
  scratch/ · snapshots/    내부에서 쓰는 임시 파일

AGENTS.md · CLAUDE.md      survey가 만드는 안내 (기존 파일이 있으면 표시된 구역만 고쳐요)
docs/agent/                survey가 만드는 프로젝트 문서 (개요·명령·관행·주의할 점)
```

## 필요한 것

- Claude Code 2.1.300·2.1.301에서 동작을 확인했어요. 이보다 낮은 버전에서 되는지는 확인하지 않았어요.
- `.claude/` 폴더는 보호 폴더라서, 권한 모드가 `default`나 `acceptEdits`면 작업 문서를 쓸 때마다 승인 창이 떠요. `auto` 모드에서는 자동 판정을 거쳐 보통 묻지 않고 진행돼요.
- `claude -p`처럼 대화 없이 실행할 때는 승인 창을 띄울 수 없어서, `default`나 `acceptEdits` 모드면 작업 문서 쓰기가 거부돼요. `--permission-mode auto`로 실행해 주세요.
- 대화 없이 실행할 때는 질문 도구(`AskUserQuestion`)도 쓸 수 없어서 signoff가 테스트 결과를 물어볼 수 없어요. 이때는 결과를 같이 적어서 불러 주세요.
  ```
  /baton:signoff <slug> 1 y, 2 n, 3 안 함
  ```

## 안에서는 이렇게 돌아가요

스킬 6개와, 스킬이 일을 나눠 맡기는 도우미 에이전트 4개로 이뤄져 있어요.

| 에이전트 | 누가 부르나요 | 하는 일 |
|---|---|---|
| `doubter` | draft | 계획에 일부러 반론을 걸어서 빈틈을 찾아요 (규모가 '정규'인 작업만 — 파일이 많거나 보안·공개 계약 등을 건드릴 때) |
| `reviewer` | inspect | 바뀐 코드(diff)와 완료 기준만 받아 리뷰해요 |
| `checker` | survey | survey가 쓴 문서가 실제 코드와 맞는지 확인해요 |
| `coder` | implement | 바꿀 파일이 많을 때(두 자릿수) Task 단위로 나눠서 구현해요 |

규칙을 고쳤다면 `claude plugin validate . --strict`로 한 번 확인해 주세요.

# baton 설계 노트 — 규칙은 왜 이렇게 생겼나

갱신일: 2026-10-18 (baton 0.3.1 기준)

## 이 문서는

`docs/guide.md`는 baton이 무엇을 하는지 설명해요. 이 문서는 규칙마다 **왜 그렇게 정했는지**를 적어요.

이 문서를 쓰는 때는 두 가지예요.

- **규칙을 고치거나 뺄 때.** 먼저 그 규칙이 무엇을 막으려고 들어왔는지 확인해요. 계기를 모르고 지우면 같은 사고가 다시 나요.
- **새 규칙을 넣을 때.** 계기, 즉 실제로 있었던 일을 적을 수 있는 규칙만 넣어요. 쓰는 틀은 맨 끝 "항목 쓰는 법"에 있어요.

모든 규칙이 여기 있지는 않아요. 초기판에서 계기 없이 이어받은 규칙은 적을 계기가 없어서 뺐어요.

계기는 baton을 사내 프로젝트에 써 본 실행 기록(작업 문서, 작업 이력, 대화 기록)에서 가져왔어요. 기록 자체는 공개하지 않아요. 여기에는 프로젝트·화면·파일·사람 이름을 뺀 사건의 줄거리와 집계 숫자만 옮겼어요.

---

## 먼저 알아 둘 것

**baton의 흐름**

- 작업 하나는 draft(계획) → implement(구현) → inspect(리뷰) → signoff(종결) 네 단계를 지나요. 각 단계는 새 세션에서 앞 단계가 남긴 **작업 문서**만 읽고 시작해요.
- 사람은 두 번 결정해요. 계획을 읽고 승인하는 **게이트1**과, 결과를 직접 확인하고 완료를 정하는 **게이트2**예요.
- 이 네 단계 밖에 survey(프로젝트 안내 문서 만들기)와 handoff(세션 넘기기)가 있어요.

**이 문서에 자주 나오는 말**

| 말 | 뜻 |
|---|---|
| 초기판 | 사내 프로젝트 안에 넣어 쓰던 버전. 이것을 프로젝트 밖으로 떼어 내 플러그인으로 만들고 baton이라는 이름을 붙였어요 |
| 계기 | 그 규칙을 넣게 만든 실제 사건 |
| 작업 문서 | 작업 하나의 계획, 구현 기록, 리뷰 결과가 차례로 쌓이는 파일 |
| AC | 완료 기준. "무엇이 돼야 하나"를 명령으로 잴 수 있게 쓴 문장 |
| Task · Verify | 계획을 나눈 단위 · 그 Task가 됐는지 재는 명령과 기대 결과 |
| 경량 · 정규 | 작업 규모. 정규일 때만 doubter가 계획을 반박해 봐요 |
| doubter · reviewer · checker · coder | 계획을 반박하는 에이전트 · 코드를 리뷰하는 에이전트 · survey 결과를 검수하는 에이전트 · 큰 작업에서 구현을 나눠 맡는 에이전트 |
| 블로커 | 고치기 전에는 다음으로 넘어갈 수 없는 지적 |
| 주의 사항 문서 | survey가 만드는 `gotchas.md`. 코드만 읽어서는 모르는데 모르면 실수하는 것들. 함정(코드·도구의 동작)·환경·경계·결정 네 구역으로 나뉘어요 |
| 작업 이력 | 끝난 작업을 한 줄씩 적는 표(`ledger.md`) |

나머지 용어는 `docs/guide.md` 11장, 에이전트 설명은 1장에 있어요.

## 2. 대표 규칙

baton의 성격을 가장 잘 보여 주는 여섯 가지예요. 항목마다 의도 → 있었던 일 → 그래서 정한 것 → 남은 문제 순서로 적었어요.

### 2.1 요청이 코드와 맞지 않으면 고치지 말고 묻는다

**의도.** 요청을 그대로 구현하기 전에, 요청이 전제한 것이 코드의 실제 상태와 맞는지 확인해요. 어긋나면 AI가 알아서 정하지 않고 사람에게 물어요.

**있었던 일.** "조건을 하나 추가해 달라"는 요청이 있었어요. 계획 단계에서 코드를 읽어 보니 그 조건을 걸 테이블은 몇 해 전에 삭제됐고, 그 쿼리를 부르는 곳도 없었어요. 계획 대신 질문을 올렸고, 사람이 판단해서 요청이 "쓰이지 않는 쿼리 삭제"로 바뀌었어요. 작업 이력 10건 가운데 요청 자체가 바뀐 유일한 작업이에요.

**전에는.** 초기판에서는 스펙 문서와 코드가 다를 때 에이전트가 "그럴듯한 쪽"을 골라 그냥 진행한 사고가 있었어요.

**그래서 정한 것.** 계획 단계에서 전제가 코드와 어긋나면 멈추고 물어요. 종결 단계에서 완료 기준을 바꿔야 한다는 결론이 나와도 그 자리에서 고치지 않고 계획 단계로 돌려보내요.

**남은 문제.** 코드만 봐서는 전제가 틀린 줄 알 수 없는 경우(운영 데이터에만 있는 사실)는 못 잡아요.

위치: `skills/draft/SKILL.md` 절차 2, `skills/signoff/SKILL.md` 절차 1 · 0.2.2

### 2.2 구현은 새 세션에서 작업 문서만 보고 한다

**의도.** 계획 대화에서 말로만 오간 가정이 구현에 섞이지 않게 해요. 문서에 빠진 게 있으면 구현하다가 드러나게 하려는 것도 있어요.

**있었던 일.** 한 작업에서는 계획 대화를 비우지 않고 바로 구현으로 넘어갔다가 대화가 길어져 자동 압축이 일어났어요. 다음 작업에서는 대화를 비운 뒤 문서만 읽고 21초 만에 첫 수정을 시작했어요.

또 다른 작업에서는 계획 단계가 사용자 메모리와 백업 폴더에 있던 옛 작업 문서를 읽고 거기 있던 해법을 가져왔어요. 문서만 보고 한 작업이 아니었던 거예요. 플러그인 있음과 없음을 비교한 실험도 같은 이유로 결과가 오염돼 다시 돌렸어요.

**전에는.** 초기판도 단계마다 새 세션을 썼어요. 이 규칙을 유지한 건 컨텍스트 한계 때문이 아니라 계획의 가정을 구현에서 떼어 내기 위해서예요. 초기판 때 다른 모델에게 문서만 주고 구현을 시켰더니 Task 넷의 Verify를 모두 통과했어요. 문서만으로 충분하다는 근거가 됐어요.

**그래서 정한 것.** 구현 단계는 새 세션에서 작업 문서, 프로젝트 문서, 코드만 근거로 삼아요. 계획 단계 끝에 `/clear`를 안내해요. handoff 문서도 같은 원칙으로 써요.

**남은 문제.** 새 세션이어도 사용자 메모리와 `CLAUDE.md`는 자동으로 읽혀요. 거기 힌트가 있으면 완전히 처음 보는 상태가 아니에요.

위치: `skills/implement/SKILL.md` 진입 조건, `skills/draft/SKILL.md` 절차 8 끝, `skills/handoff/SKILL.md` 작성 원칙 · implement 진입 조건 0.2.2, `/clear` 안내 0.2.5, handoff 0.3.0

### 2.3 작업 크기에 따라 검증 강도를 다르게 한다 (경량 · 정규)

**의도.** 작은 작업에 무거운 검증을 붙이지 않아요. 큰 작업이 작아 보여서 검증을 건너뛰는 것도 막아요.

**있었던 일.** 초기판 기록을 재 보니 두 파일 50줄짜리 작업이 66분 걸렸어요. 코드 작성은 4분이 안 됐고, 계획(약 8분)과 반박(약 8분)이 작은 작업에도 그대로 붙어 있었어요.

반대 사례도 있었어요. 6줄 변경이었지만 보안에 닿는 작업이라 정규로 보낸 일이 있었어요. 다른 작업에서는 계획이 단정한 응답 코드를 doubter가 실제 코드를 인용해 뒤집었어요.

**전에는.** 초기판에는 작은 작업용 명령이 따로 있었어요. 명령이 둘이니 어느 쪽으로 갈지 매번 사람이 판단해야 했어요.

**그래서 정한 것.** 계획 단계가 다섯 조건으로 규모를 정해요. 다섯 개가 전부 참일 때만 경량이고, 하나라도 아니면 정규예요. 정규일 때만 doubter가 계획을 반박해 봐요.

**남은 문제.** 다섯째 조건 "보안에 닿지 않음"은 경계가 애매해서 사람이 읽어야 해요. 기록에도 "아슬아슬"로 남은 판정이 있어요.

위치: `skills/draft/SKILL.md` 절차 4·6 · 0.2.5(doubter 반박은 초기판에서 이어받고, 한 명령이 다섯 조건으로 정하는 방식은 0.2.5에 새로 넣음)

### 2.4 리뷰어에게는 결론을 주지 않고 파일 경로만 준다

**의도.** 리뷰어가 구현한 쪽의 판단을 물려받지 않고, 처음 보는 눈으로 직접 확인하게 해요.

**있었던 일.** 초기판에서는 리뷰를 맡기면서 "이미 검증됨, 다시 볼 필요 없음, 앞 리뷰 블로커 0" 같은 결론 목록을 함께 넘겼어요. 리뷰어는 그 부분을 건너뛰었고, API 문서의 키 이름 불일치가 그 틈으로 빠져나갔어요.

변경 내용(diff)과 완료 기준 파일의 경로만 넘기게 바꾼 뒤에는, 리뷰가 "조건 하나가 빠져 그날 데이터 전체가 한꺼번에 등록될 수 있는" 결함을 배포 전에 잡았어요.

결과를 대화로 주고받는 비용도 계기였어요. 계획 에이전트가 결과를 대화로 돌려주자, 메인 세션이 그걸 문서에 옮겨 적는 데만 3분 넘게 걸렸어요.

**전에는.** 초기판 리뷰어 규칙에 "호출자의 결론 때문에 건너뛴 게 있으면 보고에 남긴다"를 넣었어요. 그래도 건너뛰는 것 자체는 막지 못했어요.

**그래서 정한 것.** 리뷰어에게는 `diff: 경로`, `AC: 경로` 두 줄만 넘겨요. doubter와 checker도 같은 방식이고, 셋 다 파일을 읽는 도구만 가져요.

**남은 문제.** 리뷰어는 코드를 읽기만 해요. 실제로 띄운 화면이나 실제 데이터의 빈 값은 못 봐요(`docs/guide.md` 8장).

위치: `skills/inspect/SKILL.md` 절차 2, `skills/draft/SKILL.md` 절차 6, `skills/survey/SKILL.md` 절차 6, `agents/` 세 파일의 `tools` · 0.2.2(초기판에서 이어받음)

### 2.5 리뷰 단계에서는 블로커만 고친다

**의도.** 리뷰 단계에서 스펙이 조용히 바뀌거나 작업 범위가 커지는 걸 막아요.

**있었던 일.** 초기판 때 한 작업에서 리뷰 지적을 받자 리뷰 단계가 그 자리에서 완료 기준과 코드를 함께 고쳤어요. 같은 상황을 따로 떼어 다시 돌려 보니, 옛 규칙에서는 두 번 모두 같은 일이 났고 새 규칙에서는 네 번 모두 막혔어요. 이걸 확인하고 넣었어요.

**전에는.** 초기판에는 "정책에 관한 지적은 고치지 않는다"까지만 있었어요.

**그래서 정한 것.** 리뷰에서는 블로커만 고쳐요. 제안은 기록만 하고, 완료 기준을 바꿔야 한다는 지적은 계획 단계로 돌려보내요. 작업 이력 10건 중 3건에 "리뷰 제안 n건 미반영"이 남아 있어요.

**남은 문제.** 반영하지 않은 제안이 쌓이기만 해요. 후속 작업으로 올릴 자리가 없어요.

위치: `skills/inspect/SKILL.md` 절차 4, `skills/signoff/SKILL.md` 절차 1 · 0.2.2(초기판에서 이어받음)

### 2.6 빌드 로그가 비어 있으면 "경고 없음"으로 적지 않는다

**의도.** 근거 없이 "통과"라고 적는 걸 막아요. 결과가 맞더라도 근거가 없으면 없다고 적게 해요.

**있었던 일.** 사용자 PC에는 파일을 고칠 때마다 자동으로 빌드하는 설정(전역 훅)이 있었어요. 그래서 AI가 빌드를 돌릴 때는 이미 빌드가 끝나 있었고, 빌드 도구는 할 일이 없어 4초 만에 아무것도 출력하지 않고 끝났어요. AI는 경고가 한 줄도 없으니 "경고 0"이라고 적었어요. 결과는 우연히 맞았지만 근거는 없었어요. 바로 앞 작업에서도 같은 일이 있었어요.

**전에는.** 초기판은 전체 경고 수를 기준으로 삼았다가 사고가 났고, 0.2.2에는 경고 기준이 아예 없었어요. 0.2.3에 "바꾼 줄에서 새로 난 경고만 센다"로 정했고, 0.2.4에 지금 규칙을 더했어요.

**그래서 정한 것.** 로그에 컴파일러 출력이 한 줄도 없으면 컴파일이 돈 것으로 보지 않아요. 그때는 `경고: 미확인(컴파일 생략)`으로 적어요. 규칙을 넣은 뒤 작업들은 실제로 그렇게 적었어요.

**남은 문제.** "오류 0"은 빌드 결과물이 소스보다 새것이면 인정하는데, 자동 빌드가 만든 결과물도 새것이에요. 파일 수정 시각 비교 방식을 바꿀지는 아직 정하지 않았어요.

위치: `skills/implement/SKILL.md` 절차 4 · 0.2.4

## 3. 나머지 규칙

### 3.1 원격보다 뒤처져 있으면 계획 전에 멈춘다

- **의도:** 낡은 코드 위에 계획을 세우지 않게 해요.
- **있었던 일:** 작업을 시작할 때 로컬이 원격보다 9커밋 뒤처져 있었고, 고칠 파일이 그 커밋들에 들어 있었어요. 계획 단계가 24초 만에 알아채 물었어요. 사람이 pull한 뒤에는 doubter가 계획의 줄 번호가 기준 커밋과 어긋난 것까지 잡았어요.
- **전에는:** 없었어요. 사람이 기억해야 했어요.
- **정한 것:** 원격보다 뒤처졌고 고칠 파일이 겹치면 게이트1 전에 멈추고, 작업 문서 머리에 `동기화:`로 적어요. pull은 사람이 정할 일이라 하지 않아요.
- **남은 문제:** 원격 추적 브랜치가 없는 저장소나 git 밖 파일은 못 봐요.
- 위치: `skills/draft/SKILL.md` 절차 1 · 0.2.5

### 3.2 게이트1은 계획 전체를 보여 주고, 애매한 답은 승인으로 치지 않는다

- **의도:** 사람이 읽지 않고 승인하는 걸 줄여요.
- **있었던 일:** 초기판 때 게이트1이 계획 전체 대신 요약만 보여 줬고, 사람이 28초 만에 승인했어요. "알아서 해"를 승인으로 받아들인 사고도 기록에 한 줄 남아 있어요.
- **전에는:** 초기판은 한때 "분명히 승인해야 진행" 규칙을 빼고 느슨하게 했다가 되돌렸어요.
- **정한 것:** 게이트1은 계획을 빠짐없이 한 번에 보여 줘요. 완료 기준과 사람 테스트는 표로, 확인 방법(Verify)은 한 줄씩 요약해서 보여 주고, 구현이 실제로 돌릴 명령(`검증 수단:`, `준비:`)은 그대로 보여 줘요. "좋아요", "알아서 해" 같은 답에는 같은 안내를 다시 보여 줘요. 0.2.8부터는 AC 같은 용어를 풀어 써요.
- **남은 문제:** 정말 읽고 승인했는지는 알 수 없어요.
- 위치: `skills/draft/SKILL.md` 절차 8·완료 조건 · 0.2.5, 용어 풀어 쓰기 0.2.8

### 3.3 코드로 알 수 있는 건 문서에 옮겨 적지 않는다

- **의도:** 문서가 코드와 어긋난 채 읽히지 않게 해요. 옮겨 적은 사실이 가장 먼저 낡아요.
- **있었던 일:** 주의 사항 문서에 "틀린 예"로 적어 둔 코드 조각이, 바로 그 코드를 고치는 작업 때문에 낡아 버렸어요. 두 번 반복된 뒤 "고쳐지면 낡는 예시는 주의 사항 문서에 두지 않는다"로 정했어요. 그때 코드에서 바로 알 수 있는 내용을 적은 문서 2개와 폴더별 `CLAUDE.md` 33개를 지웠어요. 주의 사항 문서의 예시 한 줄만 보고 만든 요청도 있었는데, 그 예시는 이미 쓰이지 않는 쿼리였어요.
- **전에는:** 초기판의 `CLAUDE.md`는 패턴 표와 폴더 구조를 옮겨 적었다가 136줄에서 92줄로 줄였어요. 초기판 인계 문서는 줄 번호로 위치를 가리켰는데, 다시 열 때마다 어긋났어요.
- **정한 것:** survey와 handoff는 코드로 알 수 있는 건 적지 않고, 어디를 보면 되는지만 적어요. 위치는 줄이 밀려도 틀리지 않는 이름으로 가리켜요. 코드는 함수·설정 키 이름(`파일#심볼`)으로, 계속 고쳐지는 문서는 헤딩으로 가리키고, 가리킬 이름이 없을 때만 줄 번호를 써요.
- **남은 문제:** "어디를 보면 되는지"도 파일이 옮겨지면 낡아요. survey를 다시 돌리면 잡혀요.
- 위치: `skills/survey/SKILL.md` 공통 형식 규칙, `skills/handoff/SKILL.md` 작성 원칙·문서 구조 · 0.2.5

### 3.4 Task는 AC 하나를 끝까지 채우는 단위로 나눈다

- **의도:** 마지막 Task가 끝나기 전에도 완료 기준을 하나씩 확인할 수 있게 해요. DB 컬럼 → API → 화면처럼 층별로 나누면 마지막 Task 전에는 아무것도 잴 수 없어요.
- **있었던 일:** 규칙을 넣은 뒤 한 작업에서 AC 하나가 "세 헬퍼가 …"처럼 여러 가지를 묶고 있어서, Task 1과 2 어느 쪽도 AC 하나를 혼자 채우지 못했어요. 규칙 문구와 어긋난 일로 기록됐어요. AC를 쪼갰어야 했어요.
- **전에는:** 초기판에는 "Task 하나는 5파일 이내"라는 크기 규칙뿐이었어요.
- **정한 것:** Task는 AC 하나를 끝까지 채우는 단위로 나누고, 층별로 나누지 않아요. doubter도 층별로 나눈 계획을 찾아요.
- **남은 문제:** 규칙 문구와 계획 단계의 완료 조건("Task마다 끝까지 채우는 AC 하나 이상")에는 걸리지만, AC가 여러 동작을 묶어 쓰여 있으면 계획 단계가 스스로 알아채지 못하고 넘어갈 수 있어요. 위 작업도 미리 막히지 않고 기록에만 남았어요.
- 위치: `skills/draft/SKILL.md` 절차 5, `agents/doubter.md` · 0.2.5

### 3.5 빌드는 제한 시간을 두고, 잠금에 걸리면 기다리지 않는다

- **의도:** 세션이 빌드를 기다리느라 시간을 다 쓰지 않게 해요. 사람이 띄운 프로그램은 건드리지 않아요.
- **있었던 일:** 초기판 구현 에이전트가 실행 중인 서버가 잡고 있던 빌드 결과물 잠금에 걸려 7분 넘게 기다렸어요. 그 사이 구현 에이전트를 하나 더 띄워 2분 가까이 더 썼어요. 전체 55분 중 코드 작성은 4분이 안 됐어요. 프런트엔드 쪽에서는 빌드 확인이 전체 통합 빌드를 불러 22분 넘게 멈췄고, 사람이 두 번 끼어들었어요. baton으로 온 뒤에도 한 작업에서 자동 빌드가 시간 초과로 세 번 실패했어요.
- **전에는:** 초기판 구현 에이전트에도 "제한 시간 120초, 잠금이면 다시 시도하지 않음"은 있었어요. "프로세스를 끝내지 않는다"는 baton에서 넣었어요. 실제로 끝내 버린 사고는 없지만, 개발 서버는 사람이 띄운 것이라 선을 그었어요.
- **정한 것:** 빌드는 로그 파일에 남기고 제한 시간을 둬요. 잠금에 걸리면 다시 시도하지 않고 `빌드 미완`으로 적어요. 사람이 띄운 프로세스는 끝내지 않아요. 구현 에이전트는 다른 에이전트를 띄울 수 없어요.
- **남은 문제:** 자동 빌드 설정과 세션의 빌드가 부딪히는 것 자체는 못 막아요. 자동 빌드를 끄자는 안은 사람이 기각했어요.
- 위치: `skills/implement/SKILL.md` 절차 4, `agents/coder.md` · 0.2.2(초기판에서 이어받음)

### 3.6 구현 전에 사본을 떠 두고, 커밋된 뒤에만 지운다

- **의도:** 리뷰할 때 이번 작업이 바꾼 것만 보이게 해요.
- **있었던 일:** 한 작업은 대상이 git 밖 쿼리 파일이라, 리뷰에서 무엇이 바뀌었는지 비교할 기준이 없었어요. 구현 전에 사본을 떠 두니 다음 작업에서는 사본과 비교해 이번 변경 세 곳만 골라낼 수 있었어요. 앞 작업에서 더한 7줄은 섞이지 않았어요. 지우는 시점의 문제는 실행 중이 아니라 규칙을 읽다가 찾았어요. 종결 단계가 사본을 지우는데, 사람이 커밋하기 전이라면 그 사본이 작업 전 상태의 유일한 원본이었어요.
- **전에는:** 초기판에서 커밋 안 된 변경이 섞인 파일을 `*.before` 같은 임시 사본으로 떼어 놓던 습관이 있었고, 이걸 규칙으로 만들었어요.
- **정한 것:** 대상이 git 밖이거나 고칠 파일에 커밋 안 된 변경이 이미 있으면, 구현 전에 `snapshots/{slug}/`에 사본을 둬요. 리뷰는 사본이 있는 파일은 사본과, 없는 파일은 마지막 커밋과 비교해요. 사본은 커밋된 뒤에만 지워요.
- **남은 문제:** 사본은 파일 단위라 폴더 이동이나 이름 변경은 못 잡아요.
- 위치: `skills/implement/SKILL.md` 진입 조건, `skills/inspect/SKILL.md` 절차 1, `skills/signoff/SKILL.md` 절차 5 · 사본 0.2.2, 지우는 시점 0.2.3

### 3.7 작업 전부터 있던 미커밋 변경은 사람의 것이다

- **의도:** 에이전트가 사람의 작업을 지우거나, 상관없는 변경을 커밋에 섞지 않게 해요.
- **있었던 일:** 사람이 커밋하지 않고 둔 설정 변경(서비스 시작 때 메시지 구독을 모두 끄는 설정) 때문에 구현 결과가 화면에 보이지 않았어요. 초기판 구현 에이전트가 이걸 원래대로 되돌리면서 줄끝 문자와 끝 공백까지 바꿔 놓았어요. 또 한 작업의 커밋 초안은 `git add -p`로 두 부분을 나눠 담으라고 적었는데, 다음 작업이 같은 두 줄을 건드려 나눌 수 없게 됐어요.
- **전에는:** "이 세 파일만 되돌려라" 식으로 그때그때 지시했어요.
- **정한 것:** 작업 전부터 있던 미커밋 변경은 되돌리지 않고 기록만 해요. 커밋 초안은 파일 경로를 지정해서 add해요.
- **남은 문제:** 미커밋 변경의 의도를 사람에게 묻지는 않아요.
- 위치: `agents/coder.md`, `skills/implement/SKILL.md` 진입 조건, `skills/inspect/SKILL.md` 절차 6, `skills/signoff/SKILL.md` 절차 2 · 0.2.2(초기판에서 이어받음)

### 3.8 작업 이력에 "누출 단계"를 적는다

- **의도:** 어느 단계가 약한지 숫자로 보고 규칙을 고치게 해요. 누출 단계란 뒤에서 잡힌 결함이 원래 걸러졌어야 할 단계예요.
- **있었던 일:** "뒤에 리뷰가 있으니 앞 단계가 대충 하게 되나"를 따져 보려고 초기판 작업 이력을 세어 봤어요. 앞에서 새지 않음 7건, 계획 탓 2건, 알 수 없음 32건이었어요. 대부분은 잴 수가 없었던 거예요. 그때 나온 제안 가운데 이 열 하나만 받아들였어요.
- **전에는:** 작업 이력에 이 열이 없었고, 나중에 거슬러 올라가 따졌어요.
- **정한 것:** 종결할 때 작업 이력에 누출 단계를 적어요.
- **남은 문제:** baton 작업 이력 10건은 전부 "없음"이에요. 정말 결함이 없었는지, 사람 테스트가 못 찾았는지는 가를 수 없어요.
- 위치: `skills/signoff/SKILL.md` 절차 3 · 0.2.2

### 3.9 사람의 답은 주의 사항 문서로 돌아오되, 사람이 승인해야 들어간다

- **의도:** 사람이 답한 내용이 대화와 함께 사라지지 않고 다음 작업에 쓰이게 해요. 주의 사항 문서는 사람이 승인한 것만 늘어나게 해요.
- **있었던 일:** 0.2.6 직후 작업에서 처음 돌아가는 걸 봤어요. 주의 사항 문서의 "확인 못 함" 질문이 계획의 전제로 들어가 답한 날짜와 함께 남았고, 종결 단계가 주의 사항 문서에 넣을 제안을 냈어요.

  0.2.7에 주의 사항 문서를 네 구역으로 나눈 건 사용자가 "함정 파일의 의도가 볼 때마다 의문"이라고 해서였어요. 기존 항목을 세어 보니 진짜 함정 14~15개, 환경 5개, 경계 3개가 섞여 있었어요. 실제로 에이전트 행동을 바꾼 건 환경·경계 쪽(경로를 지정한 add, 빌드 생략 등)이었어요.

  에이전트가 주의 사항 문서를 직접 고치지 않게 한 건 사용자의 "함정에 그걸 왜 넣어, 매번 할 때마다 수정할래?"에서 나왔어요.
- **전에는:** 초기판은 메인 세션이 주의 사항 문서에 직접 추가했어요.
- **정한 것:** survey는 근거를 못 댄 것을 주의 사항 문서의 `## 확인 못 함`에 질문으로 남겨요. 계획 단계가 이 질문을 함께 묻고, 답은 계획의 전제로 남아요. 종결 단계는 주의 사항 문서에 넣을 제안만 내고, 사람이 승인해야 반영돼요. 주의 사항 문서는 함정·환경·경계·결정 네 구역이에요.
- **남은 문제:** 계획에는 답한 사람이 기록되지 않는데, 주의 사항 문서의 근거에는 `답: {답한 사람}`이 필요해요.
- 위치: `skills/draft/SKILL.md` 절차 1, `skills/signoff/SKILL.md` 절차 4, `skills/survey/SKILL.md`, `agents/checker.md` A.7 · 질문 순환 0.2.6, 네 구역 0.2.7

### 3.10 보고는 작업 문서와 같은 언어로 쓴다

- **의도:** 사람이 읽는 글이 갑자기 영어로 나오지 않게 해요.
- **있었던 일:** survey 첫 실행 보고가 영어로 나왔어요. 다른 작업에서는 게이트1 글이 영어로 나와 사용자가 "갑자기 왜 영어로 답변해?"라고 했어요. 플러그인 없이 돌린 비교 세션도 첫 보고 두 번이 모두 영어였어요.
- **전에는:** 없었어요.
- **정한 것:** draft는 요청과 같은 언어로 작업 문서와 게이트1을 쓰고, implement·inspect·signoff는 보고와 게이트 안내를 작업 문서와 같은 언어로 써요. 작업 문서가 한국어면 보고도 한국어예요. 명령에 영문 작업 이름만 넘겨도 마찬가지예요. survey와 handoff는 따를 작업 문서가 없어서 기준이 달라요. survey는 저장소에 있는 문서의 언어(없으면 사용자의 언어)로, handoff는 대화에서 쓴 언어로 써요.
- **남은 문제:** 요청에 여러 언어가 섞여 있으면 어느 쪽을 따를지 정하지 않았어요.
- 위치: `skills/implement`·`inspect`·`signoff`의 `SKILL.md` 진입 조건 · 0.2.2, `skills/draft/SKILL.md` 진입 조건 · 0.3.1. 다른 기준은 `skills/survey/SKILL.md` 공통 형식 규칙, `skills/handoff/SKILL.md` 작성 원칙

## 4. 넣지 않기로 한 규칙

### 사람 테스트를 건너뛰어도 완료할 수 있게 둔다

- **있었던 일:** 사람 테스트 답이 너무 빨리 들어온 작업이 여럿 있었어요. 한 작업은 여섯 항목 전부 "예"가 26초 만에, 다른 작업은 11초 만에, 또 다른 작업은 답 네 개가 7초 안에 들어왔어요. 실제로 돌려 봤다고 보기 어려워요.
- **나온 제안:** 0.2.7 때 "확인 안 한 항목이 하나라도 있으면, 사람이 따로 받아들이겠다고 해야 완료"로 바꾸자는 제안이 있었어요.
- **넣지 않은 이유:** 완료 여부는 사람이 정한다는 것이 baton의 원칙이라 규칙은 바꾸지 않았어요. 그래서 지금은 사람이 돌려 보지 않고도 완료할 수 있어요. 이 한계는 `docs/guide.md` 8장에 적어 뒀어요.
- **참고:** 확인 안 한 항목으로 가는 경로(`미검증`, 누출 단계 `미정`)는 실행에서 한 번도 쓰이지 않았어요.

## 항목 쓰는 법

규칙을 새로 넣거나 바꾸면 3장에 이 틀로 적어요. 대표 규칙으로 올릴 때는 2장처럼 같은 칸을 문단으로 풀어 써요. **있었던 일**을 적을 수 없으면 규칙을 넣지 않아요.

```
### {규칙을 한 문장으로}

- 의도: 무엇을 지키려는 규칙인가
- 있었던 일: 실제로 무슨 일이 있었나 (이름·경로 없이)
- 전에는: 이전 규칙이나 규칙이 없던 상태, 왜 안 됐나
- 정한 것: 지금 규칙이 하는 일
- 남은 문제: 이 규칙으로도 못 막는 것
- 위치: 규칙 원문 위치 · 들어간 버전
```

제안을 따져 보고 넣지 않기로 했으면 4장에 있었던 일 · 나온 제안 · 넣지 않은 이유를 적어요. 다음에 같은 제안이 나왔을 때 이미 한 번 판단했다는 걸 알 수 있게요.
